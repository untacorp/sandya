# Backend Architect Skill

This skill equips the agent to transform high-level requirements, user flows, database schemas, and product documentation into **industrial-grade Backend Architecture and Business Logic Plans**. It ensures backend systems are robust, scalable, secure, strictly type-safe, fault-tolerant, and ready for distributed or local-first offline execution.

---

##  Core Architectural Principles

Every backend architecture plan generated by this skill adheres to these enterprise engineering standards:

1. **Clean / Hexagonal Layer Isolation**:
  - **Domain Core (Entities & Aggregates)**: Pure business rules, zero framework dependencies, strict invariant enforcement.
  - **Application Layer (Use Cases / Commands / Queries)**: Orchestrates business workflows, transaction boundaries, state transitions, and domain events.
  - **Infrastructure / Adapter Layer**: Database ORMs (Drizzle/Prisma), external API clients, message brokers (BullMQ/RabbitMQ/Kafka), and file storage.
  - **Interface / Delivery Layer**: API controllers (REST, tRPC, GraphQL, Server Actions, WebSockets, gRPC, CLI).

2. **Contract-First & Type-Safe API Design**:
  - Explicit request and response validation contracts using **Zod** or **TypeBox**.
  - Uniform error taxonomy following **RFC 7807 Problem Details** (`type`, `title`, `status`, `detail`, `code`, `invalid_params`).
  - First-class support for **REST**, **tRPC**, **GraphQL** (with DataLoader & query complexity limits), **Server Actions**, and **WebSockets / SSE**.
  - Idempotency support for mutation endpoints via `Idempotency-Key` headers backed by distributed locks & cached responses.

3. **Deterministic Business Invariants & Finite State Machines (FSM)**:
  - Complex entity lifecycles MUST be modeled as explicit state machines with guard conditions, allowed transitions, and atomic side-effects.
  - Concurrency control via **Optimistic Locking** (`version` counter / timestamps) or targeted **Pessimistic Locking** (`SELECT FOR UPDATE`) to prevent race conditions.

4. **Resilient Transaction & Outbox Boundaries**:
  - Every write operation that triggers side-effects (emails, webhook dispatches, background jobs, sync packets) MUST use the **Transactional Outbox Pattern** to ensure zero event loss and atomic commits.
  - Idempotent event consumers with Dead Letter Queue (DLQ) isolation and exponential backoff with full jitter.

5. **Defense-in-Depth Security & Cryptographic Integrity**:
  - Multi-layered authorization: Role-Based (RBAC) + Attribute-Based (ABAC) permission checks evaluated at the application use-case boundary.
  - Cryptographic protections: **Ed25519** digital signatures for verifiable payload authenticity, **Argon2id** for password hashing, and **AES-256-GCM** for data-at-rest field encryption.
  - Sliding window rate limiting, CORS/CSRF protections, and strict tenant isolation middleware.

6. **Transport-Agnostic & Distributed / Local-First Synchronization**:
  - Native support for offline-first data engines: Event-Sourcing mutation streams, vector clocks, Last-Write-Wins (LWW), and 3-way merge conflict resolution.
  - Protocol-agnostic payload ingestion capable of handling standard HTTP/JSON, binary protobufs, P2P mesh packets, animated QR frame chunking, or optical/acoustic data carriers.

##  Detailed Phase Breakdown

### Phase 1: System Topology & Bounded Contexts
- Map out the system boundary, high-level architecture (Modular Monolith, Hexagonal Core, or Microservices), and data stores.
- Extract domain aggregates and define bounded contexts (e.g. `Auth`, `EvacueeIntake`, `LogisticsDistribution`, `SyncEngine`, `Billing`).

### Phase 2: Domain Logic & State Machine Modeling
- Define core domain entities, value objects, and business invariants (e.g. "Stock cannot drop below zero", "An evacuee cannot be checked in twice without checkout").
- Formulate Mermaid state diagrams for entity lifecycles:
  ```mermaid
  stateDiagram-v2
  [*] --> Draft
  Draft --> PendingReview : Submit() [HasItems && ValidSignatures]
  PendingReview --> Approved : Approve() [UserIsAdmin]
  PendingReview --> Rejected : Reject() [ReasonProvided]
  Approved --> Dispatched : Dispatch()
  Dispatched --> Completed : AcknowledgeReceipt()
  ```

> Consult [Business Logic & State Machines Guide](./references/business-logic-and-state-machines.md).

### Phase 3: API Contracts & Interface Design
- Select the delivery mechanism (REST, tRPC, GraphQL, Next.js Server Actions, WebSockets).
- Provide explicit **Zod request schemas**, response models, HTTP status codes, and GraphQL types.
- Specify standardized **RFC 7807 Problem Details** error schemas and GraphQL error extensions.
- Define `Idempotency-Key` caching and mutation locking mechanics.

> Consult [API & Contract Design Guide](./references/api-and-contract-design.md).

### Phase 4: Use Case Pipelines & Transaction Boundaries
- Detail the exact step-by-step pipeline for critical Commands (Writes) and Queries (Reads):
  1. Authentication & RBAC/ABAC permission check.
  2. Input validation & sanitization via Zod.
  3. Begin database transaction (ACID boundary).
  4. Hydrate aggregate root from repository with locking (optimistic/pessimistic).
  5. Execute domain methods and validate business invariants.
  6. Persist aggregate changes to database.
  7. Write domain events to `transactional_outbox` in the same transaction.
  8. Commit transaction.
  9. Trigger async dispatcher / return sanitized response DTO.

### Phase 5: Event-Driven Workflows & Background Jobs
- Detail asynchronous processing using BullMQ, Redis Streams, or message brokers.
- Specify worker queue configurations, job payloads, concurrency limits, retry intervals with backoff jitter, and Dead Letter Queue (DLQ) alerts.

> Consult [Event-Driven & Background Jobs Guide](./references/event-driven-and-background-jobs.md).

### Phase 6: Security, Auth & Cryptography
- Detail authentication flows (Session cookies, JWT with sliding refresh tokens, API keys).
- Define RBAC / ABAC permission matrix mapping Roles to Actions and Resource scopes.
- Specify cryptographic signing and verification (e.g. Ed25519 signatures for tamper-proof audit records or offline QR payloads).
- Set rate limiting policies per IP / user token.

> Consult [Security, Auth & Crypto Guide](./references/security-auth-and-crypto.md).

### Phase 7: Local-First / Distributed Sync Engine
- (If applicable) Specify synchronization protocols:
  - Event Sourcing mutation replay.
  - Conflict resolution rules (Last-Write-Wins with Lamport/Vector clocks, 3-way merge).
  - Packet chunking, Reed-Solomon parity checksums, animated QR, or P2P mesh data interchange.

> Consult [Sync & Distributed Engines Guide](./references/sync-and-distributed-engines.md).

### Phase 8: Output Delivery & Roadmap
Format the complete specification using the [Backend Plan Template](./references/backend-plan-template.md) and save it in `docs/backend/<feature-name>-plan.md` or present it as a planning artifact.
